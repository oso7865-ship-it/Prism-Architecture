# ADR 작성과 영역별 번호 규칙

> ID: `ADR-GUIDE` · 소유: `documentation` · 기준: `2026-09-25`
> 읽는 때: 아키텍처 결정을 추가하거나 대체할 때

[영역·ADR 맵](../decisions/DECISIONS.md)에서 대상 영역을 고른다. 현재 정책은 각 소유 문서가 기준이며 ADR은 결정 이유와 이력을 기록한다. 전체 ADR을 기본 컨텍스트로 읽지 않는다.

## 번호와 소유권

ID는 `ADR-영역-세자리번호`, 파일명은 `ID-영문-slug.md`다. 영역별로 001부터 증가시키며 폐기·기각 번호도 재사용하거나 재정렬하지 않는다. 여러 영역에 걸치면 주 책임 영역 한 곳에 작성하고 관련 소유 문서에 링크한다. 영역을 추가할 때 DECISIONS와 context-map.json의 adr_areas를 함께 갱신한다. 내용 없는 영역 폴더는 미리 만들지 않는다.

## 작성 시점

의존성 경계, 기술 선택, 공개 API·데이터·상태 계약, 분석 의미, 권한·반출, 실행·배포·운영 정책처럼 아키텍처가 바뀔 때마다 새 ADR을 만든다. 기존 계약을 그대로 구현하는 작업, 오탈자, 동작 변화 없는 내부 정리는 새 ADR 대상이 아니다.

1. 관련 소유 문서와 해당 영역의 ADR만 읽는다.
2. 다음 번호로 [템플릿](TEMPLATE.md)을 복사하고 배경·대안·결정·영향·검증을 작성한다. 결정을 제안하는 단계는 PROPOSED로 기록한다.
3. 이미 사용자가 결정했거나 위임한 범위에서 확정한 결정은 ACCEPTED로 기록하고 근거를 명시한다. 불필요하게 재승인을 요구하지 않는다. 미정 항목은 OPEN_ITEMS에 유지한다.
4. 현재 계약의 소유 문서, 직접 소비자, 해당 코드·테스트를 같은 변경에서 갱신한다. 설계만 변경했다면 구현·검증 미완료를 명시한다.
5. DECISIONS의 영역·이력 맵과 context-map.json의 documents·adr_records·영역 작업을 갱신한다. 새 ADR은 해당 영역의 adr 작업 읽기 목록에 추가한다.
6. validate_docs.py를 실행하고 영향받은 구현 테스트를 수행한다.

## 상태와 대체

- PROPOSED: 아직 결정되지 않은 제안.
- ACCEPTED: 채택된 결정. 구현·검증 완료를 의미하지 않는다.
- BASELINE: 기존 문서에서 이관한 설계 기본값. 사용자 개별 승인이나 검증 완료를 의미하지 않는다.
- REJECTED: 검토 후 채택하지 않은 제안. 이유를 남긴다.
- SUPERSEDED: 새 ADR로 대체된 과거 결정.

PROPOSED는 논의 중 수정할 수 있다. ACCEPTED/BASELINE의 결정 내용을 소급 덮어쓰지 않는다. 변경 시 새 ADR에 supersedes, 이전 ADR에 superseded_by를 기록하고 이전 상태를 SUPERSEDED로 바꾼다. 두 필드는 context-map.json과 문서에 같은 링크로 기록한다. 오탈자·깨진 링크·이력 메타데이터 정정은 허용한다. 일부만 변경한다면 이전 ADR의 유지되는 결정을 새 ADR에도 명시하여 대체 범위를 분명히 한다.

기존 D/C 번호는 이관표로 추적하며 앞으로 새 D/C 번호는 발급하지 않는다. 문서 규칙만으로 모든 코드 변경을 자동 탐지하지는 못하므로 리뷰에서 ADR 대상 여부를 확인한다.
