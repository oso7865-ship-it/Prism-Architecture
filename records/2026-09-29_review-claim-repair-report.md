# 전달 실패·원인 설명·수정안 보수 결과

2026-09-29. 사용자 ‘1번만’ 범위의 구현과 제한 표본 검증을 마쳤다. 알려진 문제3종은 최종 반복에서 분류 오류로 거부되거나 잘못된 분기를 확정 설명하지 않았다. 일반 코드 전반의 의미 품질은 미통과 상태를 유지한다. 정상 코드에서 요구사항을 추측한 오탐1건이 남았다. Git 반영·원격 CI·EC2 배포는 수행하지 않았다.

## 무엇을 왜 바꿨는가

| 문제 | 원인 | 보수 결과 | 적용 한계 |
|---|---|---|---|
| int 곱셈 결함을 찾고도 응답 전달 실패 | 이미 아는 발생 조건을 미확인 전제로 적어 SUPPORTED 계약 위반 | 조건 관계를 출력 스키마에 게시하고 지침 보강. C4 결함3/3·정상3/3 전달 | 서버의 전제 삭제/확정 승격 없음. 향후 잘못된 형식은 여전히 거부 |
| CA 빈 문자열에 잘못된 helper 분기 설명 | 기본값·실제 경로를 모델이 재서술하며 왜곡 | 제공된 순수 코드·단언을 제한 계산하고 해당 차이를 서버가 설명. 결함3/3·정상3/3 | 이번 CA3건은 모델 의미 정확도 향상이 아니라 서버 설명으로 교체한 결과 |
| range 수정안이 정상 반환값까지 변경 | 0 입력 오류만 고치고 양수의 기존 `[0]` 계약을 무시 | 검증 호출에 반례 전달. 최종 반례가 남으면 제안 표시를 확인 안내로 대체 | 유료 C4에서는 차단 대상 구체식이 나오지 않아 실제 차단은 회귀 테스트로 검증. 자연어 전체 의미 검증 아님 |

선택적 짧은 계약 인용은 실제 제공 범위와 대조하고 저장 전에 제거한다. 잘못된 구조화 수정 식으로 자연어 range 검사를 우회할 수 없게 했다. 코드 원문/권한/동의/호출 예산은 유지한다. 화면에는 계산 출처를 ‘코드 계산에서 발견한 차이’로 구별한다.

## 설계와 비교 과정

[사전 계획](2026-09-29_review-claim-repair-plan.md)의 최대240회 내에서4개 후보를 순차 비교했다. [최종 동결 설정](quality-evaluations/claim-repair-20260929/C4-config.json)에 사례/하네스/구현 해시를, 같은 배치의 calls/results 디렉터리에 원시 공개·합성 평가 자료를 보존한다. 과거 실패 결과를 덮어쓰거나 정상 사례의 정답을 변경하지 않았다. 실제 비공개 PR 소스를 새로 전송하지 않았다.

| 후보 | 외부 호출 | 평가 | 형식 유효 | 결함 위치 누락 | 정상 오탐 | 실제 설명 검수 |
|---|---:|---:|---:|---:|---:|---|
| C1: 조건 스키마·검증 반례 | 36 | 18 | 18 | 2/9 | 2/9 | CA 경로 오해 재발, 미채택 |
| C2: 기본값·선택 분기·반환값 관측 | 36 | 18 | 17 | 2/9 | 2/9 | `type=json_object` 추가 필드 오류1건, 원인·제안 오류 잔존 |
| C3: 계약 인용·전체 문장 검수 | 36 | 18 | 18 | 0/9 | 0/9 | CA1회에서 조건 과장·효과 없는 수정안, 의미 미통과 |
| C4: 지원 가능한 단언 차이의 서버 설명 | 132 | 66 | 66 | 0/32 | 1/34 | 목표3종은 아래 검수. 전체66건 의미 통과를 주장하지 않음 |

C4는 기존54사례(36합성+6공개 최소 재현+12이전 보수 사례)를 각1회 평가하고, 목표3종과 정상 대조3종을 추가2회 반복했다. 회귀54건은 결함26/26 위치 도달·정상27/28 무지적이다. 집중18건은 결함9/9 도달·정상9/9 무지적이다. 이 둘은6건이 겹치므로 합계는66건이다. 새 독립 holdout 평가가 아니라 이미 본 회귀 표본이다.

위치·형식 자동 채점은 원인 설명이나 수정안의 정확성을 채점하지 않는다. 평가 파일의 semantic_explanation_verified=false를 일괄 true로 바꾸지 않았다. C3가 점수상 통과했는데도 채택하지 않은 이유다. C4에는 AI 항목31개와 서버 계산 항목3개가 있으며 결과의 출처를 섞어 모델 정확도라고 부르지 않는다.

정상 대조 `0add10c208ec`/`54ae24d8d95c`/`5e22872c605b`는 각각3회 무지적이었다. 기존 known-case의 잘못된 구체 수정 코드 재발은 관찰하지 않았지만 반복3회가 미래 오류 부재를 증명하지 않는다.

남은 오탐은 `898c474a9d7d`다. 계약은 호출자의 nested dictionary를 변경하지 않는 것이고 복사본 수정 후 원본 값을 반환하는 코드가 이를 만족한다. 모델은 ‘수정한 값9를 반환해야 한다’는 제공되지 않은 요구사항을 추정했다. 해당 응답/라벨을 보존했고, 자동으로 정답 처리하거나 해당 파일명만 예외로 막지 않았다. 다음 품질 작업에서는 코드의 관측 결과와 요구사항 위반 주장을 더 분리하고 독립 라벨 사례로 검증해야 한다.

## 구현과 자원 경계

- 공급자/스키마/검증: 조건별 JSON Schema, contract_quote 존재 확인, 초안+반례24,000byte 이내. 원본 코드 입력을 줄여 진단을 추가하지 않는다.
- 계산: AST 허용 구문에 대한 자체 유한 계산. Python 연속16KiB·500노드·160단계·깊이4·매개변수4·관측6개/파일·4파일. 임의 프로젝트 실행·import·eval/exec·네트워크 없음. Java는 완전한 작은 단일 곱셈 메서드만 지원한다.
- 설명: 제공 단언 불일치와 변경 경로가 함께 있는 CODE 결과만 서버 항목으로 만든다. 같은 파일·대표 줄의 모델 설명을 교체하며 다른 위치를 유지한다. 전체10개 한도, 공간 부족은 omitted로 알린다. 같은 위치의 별도 모델 결함도 교체될 수 있는 한계가 있다.
- 저장: contract_quote·소스 식·단언 인자·비어 있지 않은 문자열 값을 결과에 복제하지 않는다. 제공 코드 계산의 값 유형/정수/불리언·분기·줄을 설명한다. 원문·응답 비저장, 과거 결과 불변, DDL 변경 없음.
- 적용: 유효한 모델 응답 이후 계산 설명을 결합한다. 모델/공급자 실패 자체를 성공으로 덮지 않는다. 테스트 기대값의 진실성·전체 입력·실행 환경은 미검증이다.
