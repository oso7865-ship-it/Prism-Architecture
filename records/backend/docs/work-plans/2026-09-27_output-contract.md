# 응답 형식·질문 채택 기준 보완

- 규모: M. backend dev의 제품 리뷰 지침과 검증, architecture main의 소유 설명을 갱신한다.
- 요청: 이전 평가의 형식 실패 2건과 근거 없는 질문 1건 대처방안 적용, 리랭커/환각 방어의 실제 도입 상태 확인.
- 설계 근거: 기존 ReviewOutput 계약과 ADR-REVIEW-006을 유지한다. 원문 모델 출력은 summary/issues/limitations 세 필드이며, API의 issues/questions 분리는 서버의 후처리다. 두 형식의 혼동은 가능한 원인이지 이전 실패의 확정 원인이 아니다.
- 수정: output.md에 단일 출력 계약과 검증 가능한 정상 지적/조건부 질문/0건 예시를 둔다. checks.md에서 실제 변경 동작과 판정을 바꾸는 미확인 전제가 모두 있는 질문만 채택하도록 정리한다. 보이지 않는 호출부만으로 만든 질문은 limitations로 기록한다. 수정 제안은 영향받는 나머지 분기도 확인하도록 한다.
- 유지: strict schema, 근거 위치/변경 줄/가정 검증, JSON mode, 호출당 재시도0/출력2000토큰, 기존 평가 정답·채점. 자동 형식 보정·지적 삭제·추가 심사 모델을 넣지 않는다.
- 상태 확인: 선언 의존성, 설치된 배포 패키지, 실제 context/provider/validator 경로를 함께 확인한다. 이름 기반 관련 파일 선택을 모델 리랭커로 표현하지 않는다. 자체 가드레일의 구조 검사와 의미 판단의 한계를 구분한다.
- 제외: 새 외부 의존성/모델 설치, 검색 구조·DB·권한·API schema 변경, 과거 리뷰 재작성, 커밋·푸시·배포.
- 적용: terminal-ops, 명령 안전성/근거 검수/문서 검증. 개발 에이전트 하네스의 정책 수정은 없다.
- 위험: 로컬 API 재시작과 유료 평가. 사용자의 대처방안 적용 지시를 근거로, 앞서 제안한 동일 합성10사례 비교를 각1회/총10회 한도로 수행한다. 자동 재시도·추가 유료 배치 없음. 실제 저장소 코드와 사용자 피드백은 전송하지 않는다.
- 검증: 예시를 실제 validator로 검사 → 잘못된 형식·근거 거부 회귀 → 전체 언어 조합의24KiB 예산 → 동일10사례 실제 비교와 수동 의미 검수 → 진행 Job 확인 후 API 재시작·ready 확인 → Report.
- 롤백: 이번 제품 지침 변경만 이전 문구로 되돌리고 API 재시작한다. 기존 미커밋 작업과 결과 기록은 보존한다.
