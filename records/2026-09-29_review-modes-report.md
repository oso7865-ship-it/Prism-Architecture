변경 코드의 16KiB/파일·48KiB 합계 한도는 유지한다. 팀 문서 섹션은 최대12KiB, 코드·파일 경로·문서 입력 합계60KiB 이내다. 선택하지 않은 섹션 수를 보여 주며 모든 규칙을 읽었다고 표시하지 않는다. 문서는 비신뢰 데이터이며 시스템 지시나 실행 도구가 아니다.

수정한 평가 스키마가 과거 기준선까지 바꾸던 문제는 `evals/recall-repair/baseline-schema.json`으로 기준선 스키마를 고정해 해결했다. 기존 baseline-manifest의 SHA-256과 일치함을 확인했으며 과거 점수를 새 기준으로 덮어쓰지 않았다.

## 로컬 적용·복구

- 실제 DB 수정 전에 `pg_dump -Fc` 백업 완료: 로컬 `audit-artifacts/review-modes-20260929/before-standards.dump`.
- 백업 SHA-256: `276468FEAE1AC63D79C2C1B405A873F55643B1C5DEF8733833BBDBE5DBBE6F1E`.
- 새 테이블/목적 열만 추가하는0009 적용. 새 데이터가 있으면 downgrade는 거부한다. 실제 백업 파일의 복원 리허설까지 수행한 것은 아니다.
- DB 모델 일치 검사 첫 명령은 임시 DB 사용자 이름을 잘못 지정해 실패했다. 실제 임시 컨테이너의 기본 postgres 사용자를 확인해 수정 후 같은 검증이 통과했다. 실제 DB에는 영향이 없다.
- 로컬 서버 로그/비밀 설정은 Git에 넣지 않는다. 문서·보고서는 이 아키텍처 저장소에만 남긴다.

## 남은 경계와 사용 순서

1. 저장소 화면에서 **팀 문서 관리 → 문서 등록**으로 실제 컨벤션/구조 문서를 등록한다. 경로/예외를 지정하고 필수 규칙은 필수 검토로 표시한다.
2. PR의 **코드 리뷰 / 취약점 / 팀 규칙** 중 필요한 목적을 선택한다. 코드 점검 완료 기록을 선택하고 전송에 동의해 실행한다.
3. 결과의 코드 근거, 인용 문서 버전·섹션, 제외된 범위를 확인한다. 문서를 고치면 새 리뷰부터 새 버전을 사용한다.

기능 구현과 로컬 검증은 완료 범위다. 실제 팀 문서 기반의 사람 수용 평가, 전체 의미 품질 개선, 공개 배포/운영 인증·HTTPS/백업 정책 검증, Git 게시·원격 CI는 별도 후속이다.
