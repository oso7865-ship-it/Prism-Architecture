## 배경

단일 시스템 프롬프트만으로는 언어별 판단 기준과 품질 평가·변경 이력을 관리하기 어렵다. 검토한 코드 근거와 추가 확인 사항을 구분해야 한다.

## 결정

review/harness 패키지의 신뢰된 공통 원칙·검토 절차·출력 기준·언어별 Markdown을 서버가 조합한다. 저장소에서 가져온 지침은 실행 정책으로 승격하지 않는다. 기존 코드 반출 제한·권한·도구 미제공·엄격한 응답 검증은 서버가 강제한다.

전체 문서와 schema digest로 기존 prompt_version에 패키지 버전을 기록하고 성공 결과에 선택 모듈과 실제 system digest를 추가한다. 원문 prompt는 미보관. 모듈은 Python 패키지 자원으로 배포된다. system 입력24KiB와 user 입력24KiB를 각각 제한한다.

결과 basis는 SUPPORTED(제공된 코드 근거)/NEEDS_CONTEXT(추가 확인 필요)로 구분한다. 심각도와 별개이며 모델의 자기평가를 검증된 진실로 표현하지 않는다. 정상/결함/문맥 부족/주입 시도 corpus와 오프라인 평가기를 제공한다.

## 대안

개발 에이전트용 GENERAL_HARNESS 전체 전달은 역할·권한이 다르고 입력을 낭비한다. 저장소의 문서를 자동 시스템 프롬프트로 쓰면 신뢰 경계가 무너진다. 모든 언어 지침을 매번 보내지 않고 해당 언어만 선택한다.

## 영향과 한계

새 출력 계약에 basis가 추가된다. 과거 결과는 그대로 읽고 버전/근거가 미기록임을 표시한다. DB migration은 없다. 내용 변경은 버전 변경으로 중복 실행 키에 반영된다. fixture/scorer 통과는 모델 정확도 증명이 아니며 실제 모델의 오탐·누락은 고정 corpus의 별도 측정이 필요하다.
