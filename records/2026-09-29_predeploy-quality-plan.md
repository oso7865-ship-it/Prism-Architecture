# 실제 PR 검증과 최소 리뷰 품질 확보 계획

## 작업 계약

- 요청: 최신 변경 커밋·푸시·원격 CI, 실제 조직 PR의 요청→완료→근거 확인, 누락/잘못된 설명 개선. 실패하면 관점을 바꾸어 재평가하며 필요 시 관련 코드 취득을 확장한다.
- 규모: L. backend/frontend는 dev, architecture는 main. 기존 미커밋 변경을 보존하고 이번 요청 범위와 함께 검증한다. 보고서·평가 기록은 architecture에만 게시한다.
- 읽은 기준: CORE, REVIEW, SECURITY-PRIVACY, PACKAGE-RULES, CODE-CONVENTIONS, ADR-REVIEW-011, 기존 recall-repair·empty-source 보고서. 로컬 Git/terminal 스킬 및 GateGuard 적용.
- 위험: 승인된 외부 유료 호출·실제 PR 코드 전송. 기존 3,000회 총량의 남은 예산 안에서 호출 전 예약. 팀 하루30회·제품 요청당2회·권한/비밀 검사 유지. 대상 저장소 코드는 실행하지 않는다.
- 제외: AWS 자원 생성·공개 배포·대상 GitHub PR에 댓글/수정·과거 리뷰 결과 수정·하네스 원본 동기화. Windows DB 테스트는 피하고 Linux 격리 DB를 사용한다.

## 설계와 완료 기준

1. 기존 평가기의 실제 제품 분기(빈 답변 재검토 포함) 일치 여부부터 검사한다. 같은 입력으로 기존 실패 사례의 위치·원인·영향·수정안, 정상 오탐, 응답 형식을 분리 평가한다.
2. 누락 원인을 입력 미포함 / 모델의 연산·계약 해석 / 검증 중 손실로 구분한다. 입력이 이미 충분한 실패를 단순 예산 확대로 고치려 하지 않는다. 지침·검증·문맥 수집 변경은 근거가 있는 범위만 적용한다.
3. 최소 게이트: 기존 결함2종×3회와 정상4종×3회, 별도4언어 사례 및 기존 경계 사례에서 위치 적중뿐 아니라 최종 설명·개선안의 수동 검수까지 확인한다. 소규모 자체 평가이며 일반적인 미탐0 보장은 하지 않는다. 실패 후보·원 실행 기록은 보존한다.
4. 실제 조직 PR #49에서 최신 고정 커밋의 리뷰를 요청하여 완료 상태, 파일별 재검토 또는 근거 검증, 사이트 내 소스/줄 확인까지 검증한다. 지적 수를 억지로 늘리지 않고 0건이면 검토 근거와 제외 범위를 확인한다.
5. 변경에 맞는 테스트·보안 경계·문서 검증 후 세 저장소에 커밋·푸시한다. 정확한 커밋의 GitHub Actions 결과를 확인하고 기록한다. 원격 CI가 실패하면 원인을 수정하여 다시 확인한다.
