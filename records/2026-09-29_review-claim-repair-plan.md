# 전달 실패·원인 설명·수정 제안 보수 계획

상태: 범위 내 보수·검증 완료, 전체 의미 품질 미통과. 규모 L. 사용자 ‘1번만’ 승인 범위이며 Git 반영·EC2 배포·운영 구성은 제외한다. backend/frontend dev, architecture main을 유지하고 기존 변경을 보존한다.

## 재현과 목표

- int 곱셈 결함: 코드/계약에 이미 있는 입력 조건을 assumptions에 중복 작성해 SUPPORTED 출력이 거부된다. 서버가 전제를 삭제/확정으로 승격하지 않고, 출력 스키마의 조건 관계와 모델 지침에서 이미 알려진 발생 조건과 진짜 미확인 전제를 구별한다.
- CA 빈 문자열: 검증자가 정확한 최종 값에 도달하면서 실제 입력에서 실행되지 않는 helper 분기를 설명에 섞는다. 결과 문장은 해당 trigger의 직접 결과로 제한하고 근거·수정안 전체가 같은 경로를 설명하도록 검증 지침을 보수한다.
- range 수정안: n=0 오류 해결 과정에서 기존 성공값을 바꾸는 대안. 제한 검사 반례를 두 번째 검토에 전달하며, 최종 응답에도 동일 반례가 남으면 해당 수정 제안은 안전한 안내 문구로 대체한다. 결함·근거·반례는 보존한다. 일반 프로그램 의미 검증으로 확대하지 않는다.

## 구현/검증 경계

읽은 기준: CORE, REVIEW, RESULTS, PRIVACY, PACKAGE-RULES, CONVENTIONS, ADR-REVIEW-013. 적용: Terminal Ops, Verification Loop. 새로운 공급자·모델·의존성·도구 권한 없이 최대2회·고정 SHA·권한/취소/예약·원문 비저장·기존 입력 한도를 유지한다. 분류가 여전히 모순되면 실패로 처리하며 성공0건으로 숨기지 않는다.

먼저 기존 응답/경계 조건으로 회귀를 재현한다. 좁은 스키마·검증 입력·제안 후처리를 변경하고 Linux Docker에서 검사한다. 의미 품질은 공개·합성 실제 API 평가로 확인한다. 신규 배치 최대240호출, 현재 승인 캠페인 잔여2,594 안에서 공통 원장에 선예약한다. 예전 기록은 변경하지 않는다. 문제3종의 반복과 정상 대조, 기존54사례를 검수하며 정답/사례ID는 모델 입력에 넣지 않는다. 무관한 실험의 재실행은 하지 않는다.

채택 기준: 문제 사례의 의미 오류/분류 실패가 재현되면 원인을 더 수정한다. 정상 코드의 신규 오탐·기존 중요 누락 증가 여부도 검사한다. 제한 표본 통과를 전체 품질 통과로 부르지 않는다.

C1 집중36호출에서 형식18/18이지만 누락2·정상 오탐2와 기존 CA 분기 오해가 재발했다. C1은 품질 통과로 채택하지 않는다. C2는 제공된 작은 순수 Python 함수/리터럴 테스트에 대한 제한 상수 전파(선택 분기·기본값·반환값)와 단일 Java 정수 산술 반환식의 타입별 관측값을 추가한다. 자체 AST/정수 모델만 사용하고 Python 함수 생성·eval/exec/import·프로젝트 런타임·외부 호출은 금지한다. 지원 밖은 분석하지 않는다. 실제 실행 증거나 전체 프로그램 증명으로 표시하지 않는다. 기존600회 배치와 별개인 이번240회 상한은 유지한다.

C2에서도 잘못된 설명이 남아 C3에 계약 인용과 전체 문장 검수를 추가했다. C3의18건은 위치/형식 기준 통과지만 CA1회에서 발생 조건 과장·효과 없는 수정안이 나왔다. C4는 제공 단언과 지원 가능한 순수 코드 계산의 차이를 서버 소유 설명으로 만들고 출처를 구분한다. 잘못된 자연어 원인 재서술을 피하되 실제 테스트 실행/일반 의미 증명으로 확대하지 않는다. 같은 위치의 설명 교체·전체10개 한도·원문 비저장·모델 실패 유지 경계는 ADR-REVIEW-014에 기록한다.

완료: 총240호출, C4 회귀54건+추가반복12건. 알려진3종의 보수 결과와 정상 오탐1건을 [보고서](2026-09-29_review-claim-repair-report.md)에 남겼다. 전체 의미 품질 승인으로 확대하지 않는다.
