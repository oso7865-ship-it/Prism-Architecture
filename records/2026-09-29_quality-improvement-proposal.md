# 품질 상향 후보와 적용 순서

상태: 조사·제안 완료, 제품 미적용. 이번 작업은 기존 평가·현재 코드·공식 자료를 대조해 개선 후보를 정리하는 범위다. 새 유료 호출/제품 코드/모델 설정/배포 변경은 없다. 문서는 architecture에만 둔다. 읽은 소유 문서는 CORE, REVIEW, STANDARDS이며 기존 [품질 실험](2026-09-29_quality-lab-report.md)과 [모델 비교](2026-09-29_model-comparison-report.md)를 근거로 삼았다. 실제 정책 변경을 시작할 때 REVIEW ADR과 소유 계약을 함께 설계한다.

## 판단 근거

측정 배치는 종료했지만 전체 품질이 통과한 것은 아니다. 문제가 네 층에서 발생했다: 필요한 정보 누락, 정보를 받았지만 의미를 오해, 찾은 결함의 수정안/설명이 잘못됨, 유효한 내용이 응답 처리 규칙 때문에 사용자에게 전달되지 못함. 이를 하나의 모델 점수로 합치면 개선 방향을 잘못 고른다.

현재 `ReviewWorker`는 초안에 항목이 있으면 `apply_verification`을 호출하고, 최초 초안이 비었을 때만 파일별 재검토를 한다. `VerificationOutput`은 기존 항목의 KEEP/REVISE/DROP만 지원하며 새 항목 추가는 불가능하다. 따라서 틀린 초안이 전부 기각된 경우 실제 결함을 새로 복구할 경로가 없다. 이 구조는 코드로 확인한 사실이며, 변경 후 얼마나 좋아질지는 아직 가설이다.

## 후보 6개

|---|---|---|---|---|
| 1 | 검증 단계에 빠진 결함 발견 허용 | 잘못된 초안 삭제 후 실제 결함 미복구 | 기본2호출 유지 가능, 2차 출력·처리량 증가 가능 | 먼저 |
| 2 | 동작과 수정안의 계약 보존 검사 | 연산 오해, 정상 입력을 깨는 수정안 | 제한된 언어 연산 검사 개발, 지원 밖은 미검증 | 핵심 |
| 3 | 구조화 출력과 결과 전달 경로 정비 | JSON 필드/파일별 점검 위치 오류 | API 어댑터·스키마 호환성 검증, 의미 정확성은 별개 | 1과 함께 |

| 6 | 어려운 경우에 한정한 추론 설정 | 경계값·분기·타입 혼동 잔존 | 응답 지연/출력 증가, 실제 효과 미검증 | 뒤에 비교 |

### 1. 검증하면서 빠진 결함도 다시 찾기

2번째 호출을 초안 심사와 변경 범위 누락 검토를 함께 수행하는 계약으로 바꾼다. 기존 지적의 처리 결과, 독립적으로 발견한 새 후보, 검토한 변경 범위를 분리한다. 새 후보도 같은 SHA·전송된 근거·발생 조건·계약 위반 검증을 통과해야 한다. 초안과 같은 지적의 중복은 서버가 합친다.

기각된 지적을 억지로 유지하지 않는다. 예를 들어 양수 n에서 `[0]`이 나온다는 잘못된 지적은 삭제하되, 같은 함수의 n=0에서 ValueError가 나는 별개 결함을 검토할 수 있어야 한다. 기본 최대2회 정책을 유지하며, 호출 추가 대신 두 번째 호출의 책임을 바꾸는 실험을 우선한다. 지시가 복잡해져 성능이 나빠질 수 있으므로 현재 경로와 같은 입력으로 비교한다.

### 2. 수정안까지 맞는지 검사하기

각 결함의 구체 입력, 실제 관측 가능한 동작, 요구 동작의 출처를 분리한다. 요구 동작은 팀 규칙/명시 계약/관련 테스트에서 인용하며, 모델이 추정한 의도를 필수 요구로 승격하지 않는다. 검증은 숨은 사고과정 수집이 아니라 반환값·예외·변경된 상태 같은 확인 가능한 결과를 대상으로 한다.

이전 실험의 '모델에게 관측값을 먼저 적게 하기'나 AST 목록 추가를 그대로 반복하지 않는다. 이번 후보는 **서버가 계산 가능한 좁은 연산 결과와 모델 주장을 대조**한다. Python의 None/빈 문자열·range 인자, Java의 정수 승격/오버플로, JS의 nullish/불리언 분기처럼 지원한 구문만 해석한다. 알려지지 않은 호출·동적 타입·오버로드는 UNKNOWN으로 남긴다. 소스 문자열의 eval/exec, 저장소 import/build, 의존성 설치는 하지 않는다.

수정안은 결함 입력뿐 아니라 기존 정상 입력의 계약도 보존해야 한다. range 사례에서 n=0의 예외를 없애도 n=3의 `[0]`을 `[0,1,2]`로 바꾸는 대안은 걸러야 한다. 수정안을 입증하지 못해도 근거 있는 결함 자체는 보존하고, 제안의 확인 상태를 따로 표현한다. 수정안 검증 실패를 발견사항 전체 삭제로 처리하면 누락이 늘어난다.

실행 결과 피드백을 이용한 Self-Debugging 연구는 이 방향의 외부 근거지만 코드 생성 벤치마크 결과이며 PRism 효과를 증명하지 않는다. 프로젝트 전체 실행은 현행 범위 밖이라 초기에는 사전에 작성한 안전한 참조 연산/허용 구문 검사만 대상으로 한다. [연구 원문](https://arxiv.org/abs/2304.05128).

### 3. 형식 오류 때문에 내용을 잃지 않기

현재 제공자는 Chat Completions의 `json_object`와 서버 Pydantic 검증을 사용한다. 공식 DeepSeek Responses API는 `text.format.type=json_schema`를 안내하므로, 평가 전용 어댑터로 실제 지원 스키마와 SDK 호환성을 먼저 검사한다. 현재 어댑터에서 옵션 이름만 바꿔 된다고 가정하지 않는다. JSON Schema 준수는 근거와 의미의 정확성을 보장하지 않으므로 서버의 위치·권한·인용 검사는 유지한다. [공식 API](https://api-docs.deepseek.com/api/create-response/).

파일별 점검의 대표 변경 행처럼 서버가 이미 아는 값은 모델이 새로 추측하게 하지 않는다. 모델은 파일 ID와 검토 결과를 내고 서버가 변경 구간의 식별자를 연결하는 계약을 검토한다. 결함을 뒷받침하는 실제 근거 줄은 별도로 검증하며 임의의 변경 행으로 바꿔치기하지 않는다.

일부 항목의 검증 실패가 나머지 유효한 항목까지 지우는지도 평가한다. 부분 결과를 허용한다면 실패한 항목 수/검토 미완료 범위를 명시하고 '문제 없음'으로 표현하지 않는다. 알 수 없는 필드 제거나 잘못된 근거 줄의 무조건 보정은 도입하지 않는다.

### 4. 정보가 없는 경우에만 관련 코드를 보충하기

현재 변경 파일16KiB/전체 코드48KiB, 필수 근거 보존, 직접 호출 보호, 팀 문서 BM25 검색은 이미 존재한다. 추가 후보는 첫 검토에서 구체적으로 부족한 함수/타입/설정 ID를 지정하고, 서버가 고정 SHA에서 제한된 범위만 읽어 두 번째 검토에 넣는 방식이다. 임의 URL 탐색이나 전체 저장소 확장은 허용하지 않는다. 검색 결과에는 출처·미포함 범위를 붙이고 필수 근거가 예산을 넘으면 부분 검토로 남긴다.

팀 문서는 적용 경로·필수 규칙·버전을 먼저 고정한 뒤 검색한다. 문서에 없는 일반 취향은 팀 규칙 위반으로 만들지 않는다. 한국어 규칙과 영문 심볼 간 검색 실패를 별도로 측정한 뒤 용어 사전/혼합 검색/임베딩을 비교한다. 이미 제공된 연산을 잘못 읽는 문제에 임베딩을 우선 투입하지 않는다.

### 5. 취약점은 별도 근거원으로 탐지 범위 넓히기

코드의 데이터 흐름(입력→검사→위험 연산)을 추적하는 분석과 알려진 라이브러리 취약점 조회를 분리한다. CodeQL 문서는 구문 트리와 데이터 흐름을 구별하고 함수 안/함수 사이의 흐름 및 오염 추적을 설명한다. PRism에 지금 설치돼 있다는 뜻은 아니며, 엔진 도입 시 지원 언어·라이선스·분석 준비 비용을 비교해야 한다. 빌드가 필요한 통합은 현행 '대상 코드 실행 안 함' 정책을 별도 변경하기 전에는 채택하지 않는다. [공식 데이터 흐름 설명](https://codeql.github.com/docs/writing-codeql-queries/about-data-flow-analysis/).

의존성은 lockfile 등에서 확인된 패키지·생태계·정확한 버전으로 OSV 같은 정보원을 조회할 수 있다. 버전이 불명확하면 확정하지 않고, 취약 버전 포함과 실제 공격 경로 도달 여부를 구분한다. 원문 코드 대신 필요한 패키지 메타데이터만 취급하고 정보원 갱신 시각을 기록한다. 공개 정보원에서 결과가 없다고 안전을 인증하지 않는다. [OSV API](https://google.github.io/osv.dev/api/).

AI는 독립 분석 결과의 의미·수정 우선순위를 설명하되 원래 탐지 결과를 삭제하지 않는다. 기존 코드 리뷰/취약점/팀 규칙 탭 분리는 유지한다.

### 6. 추론 모드는 필요한 조건에만 비교

현재 Flash를 기본으로 유지한다. 이전 낮은 추론 실험과 Pro 비추론 비교만으로 높은 추론의 효과를 단정하지 않는다. 연산 검사와 모델 주장 불일치, 복잡한 분기, 문맥 부족 등 사전 정의한 조건에서 두 번째 호출만 추론 설정을 바꾸는 후보를 비교한다. 같은 모델/자료에서 추론 설정과 출력 예산을 나누어 실험한다. 자기평가 확신도만으로 어려움을 판정하지 않는다. 호출 수가 같아도 토큰·시간이 증가할 수 있어 제한과 실패 시 표시를 설계해야 한다.

## 추천 실행 순서와 통과 기준

**1+3 → 2 → 필요한 경우4·5 → 6** 순서다. 모든 변화를 한 번에 넣지 않고 대조군, 단독 변경, 효과가 확인된 조합을 구분한다. 개선 수치는 사전 약속하지 않는다.

기존42사례는 회귀셋으로만 쓰고 새로운 함수·호출 관계·실제 팀 문서와 독립 사람이 확인한 정답을 별도로 동결한다. 같은 사례를 이름만 바꾼 자료는 독립 검증셋으로 세지 않는다. 결함 탐지, 근거 위치, 원인 설명, 수정 후 정상 동작, 정상 오탐, 질문 필요성, 최종 전달 성공률을 분리한다. 새 미사용 사례의 결과를 본 뒤 튜닝하면 그 자료는 회귀셋으로 전환한다.

고정 회귀셋에서는 중요 결함의 새 누락0·정상 오탐 증가0·위험한 수정안 증가0·검증/전달 실패 증가0을 요구한다. 새 검증셋에서는 유형별 건수·분모·반복 편차를 함께 보고해 작은 차이를 우월성으로 단정하지 않는다. 출력 제한과 p95 지연·토큰 상한을 실험 전에 고정한다. '발견0건'과 '검토하지 못함'은 끝까지 분리한다.

이번에는 조사만 수행해 유료 호출이 추가되지 않았다. 캠페인은1,910/5,000회, 잔여3,090회다. 다음 배치의 자료·비교 조건·최대 호출 수를 먼저 정한 뒤 기존 원장으로 집계한다.
