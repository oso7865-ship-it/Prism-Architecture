# 실제 PR·품질 검증과 Git 반영

## 결론과 범위

[사전 계획](2026-09-29_predeploy-quality-plan.md)에 따라 기능 검증과 의미 품질 평가를 분리했다. 실제 조직 PR의 요청→완료→파일별 재검토→고정 커밋 코드 열람은 통과했다. **AI 리뷰 최소 품질 기준은 미통과**다. 구조·줄 검증 성공이나 자동 점수만으로 품질 확보를 선언하지 않는다. 공개 배포·AWS 자원 생성·main 병합은 이번 범위가 아니다.

- 읽은 문서: CORE, REVIEW, SECURITY-PRIVACY, PACKAGE-RULES, CODE-CONVENTIONS, ADR-REVIEW-011, 기존 recall-repair/empty-source 보고서.
- 적용: 로컬 Git Workflow·Terminal Ops, Computer Use. 설계·구현·검증·후속 기록을 architecture에만 관리한다.
- 기존 미커밋 코드 보기·빈 답변 재검토·AWS/EC2 설계를 보존하고 함께 검증한다. backend/frontend는 dev, architecture는 main에 반영한다.

## 반영한 변경

| 문제 | 변경 | 확인 방법 |
|---|---|---|
| 평가기가 빈 초안이면 종료하여 실제 제품의 두 번째 호출을 재현하지 못함 | 빈 초안도 파일별 재검토하고 호출 전 예약·사용량·실패 단계를 기록 | 성공/실패 단위 검사, 실제 유료 기준선 |
| 다른 변경 파일의 hunk 밖에 있는 호출 함수가 후보에서 빠짐 | 이미 안전하게 취득한 다른 변경 파일의 이름 일치 정의도 직접 호출 보호 후보에 포함 | 별도 파일의 가드 정의가 선택되는 회귀 검사 |
| 리뷰에서 GitHub로 이동해야 코드 확인 가능 | 제공 파일·근거 줄에서 고정 SHA의 코드를 사이트 안에 열람, 페이지/줄 제한과 권한 재검사 | Linux API 검사, 실제 PR의 28줄 열람 |
| 빈 초안을 검토 완료로만 표시 | 모든 변경 파일별 관찰 결과와 근거 줄을 요구하는 재검토 | strict schema/변경 줄/삭제 전용/실패 경로 검사 |
| 새 질문 2개가 있어도 이전 회차 비교에 신규 0개 표시 | 개선 제안과 질문을 함께 비교, 과거 합쳐진 표현도 동일하게 분류 | 프론트 회귀 검사, 실제 화면 신규 2개 확인 |

취득 한도는 변경8파일·관련4파일·파일당16KiB·전체48KiB를 유지한다. 새 모델/리랭커를 제품에 켜지 않았으며 분석 대상 코드를 실행하지 않았다. 사용자의 제품 코드는 평가 정답을 넣기 위해 수정하지 않았다.

## 실제 PR 사용 흐름

- 대상: `1-team-whyNot-chapchap/chapchap-customer-service` PR #49.
- 실행 ID: `0b73b716-c909-45c4-90eb-55b81bb4c092`, HEAD `562e52893788e68abccee20cd82d4b4265a0b6db`.
- 완료: 2026-09-29 12:27:55 KST. 약17초, 외부2회, `EMPTY_RECHECKED`.
- 변경8개 파일별 검토 결과, 전체 제공12파일, 제외5개. 개선 제안0·질문2.
- 파일별 근거에서 사이트 내 소스를 열어 1~61줄, 대표28줄, 동일 고정 SHA의 GitHub 링크를 확인했다. 열람하는 넓은 소스 범위가 모두 AI에 제공됐다는 뜻은 아니다.
- **기능 PASS / 의미 FAIL**: 두 질문 모두 제공되지 않은 반대 잠금 경로에 의존했다. 실제 결함으로 인정할 수 없으며 단순히 질문 수가 늘었다고 개선으로 채택하지 않는다.
- [호출·검증 메타데이터](quality-evaluations/quality-0929-real-pr.json). 조직 소스·리뷰 본문은 공개 기록에 복사하지 않았다. 화면 증거는 로컬 `audit-artifacts/quality-20260929/real-pr-source.png`에만 보관한다.

## 여러 접근의 유료 비교

핵심 진단 사례는 결함2종과 정상4종이다. 아래 자동 점수는 위치/형식 기준이며 의미 정확도 수치가 아니다. 실패 응답을 고쳐 성공 기록으로 덮어쓰지 않았다. 차단 사례의 최종 주장을 에이전트가 검수했으며 나머지 모든 응답의 독립 사람 검수가 완료된 것은 아니다.

합성90리뷰·177호출, 실제 PR 1리뷰·2호출로 **이번179회**, 승인 총량 **1,539/3,000회**, 남은 **1,461회**다. 시간 초과/실패도 예약한 호출에 포함한다. [집계와 결과 해시](quality-evaluations/quality-0929-summary.json), [누적 원장](quality-evaluations/usage.json)을 보존했다.

추론/Pro 후보는 출력8192token·호출60초의 평가 전용 프로필이다. 혼합 모델 기록의 원래 `max_output_tokens=2000`은 초안 설정이며 검수는 Pro/low/8192였다는 정정을 집계 파일에 기록했다. 평가기에 단계별 모델·예산 및 신뢰 지침 스냅샷 기록을 추가했다. 최종 탈락 [지침 스냅샷](quality-evaluations/quality-0929-candidate-harness.json)을 보존했다. 모든 이전 변형의 지침 전문까지 재구성 가능하다고 주장하지 않는다.

채택 후보는 없다. 실제 제품은 `deepseek-flash`, 추론 비활성, 회당2000token/60초, 최대2회, 지침 `rh1-b1c775a23f028ad3`를 유지한다. 평가 전용 클래스는 제품 provider factory에 연결하지 않았다. 핵심 사례에서 이미 탈락했으므로 독립4언어·확장 회귀 평가까지 통과한 것으로 처리하지 않는다.

## 검증과 실행 환경

- 최종 자동 검사: backend 382 tests PASS(72.81초), Ruff 검사/형식160파일 PASS, mypy121파일 PASS. 기존 Pydantic alias 경고1건은 남아 있다.
- 프론트: 119 tests, 타입 검사·프로덕션 빌드 PASS.
- 백엔드: Linux 격리 PostgreSQL17에서 최종 전체 검사 PASS. Windows에서 DB 통합 검사를 실행하지 않았다.
- Docker 재시작을 막던 오래된 0byte 런타임 소켓 디렉터리를 이름 변경해 보존한 후 복구했다. 기존 DB 볼륨을 삭제/초기화하지 않았다.
- 로컬 API는 Windows SelectorEventLoop로 실행해야 DB 작업이 가능했다. uvicorn의 현재 loop factory가 Proactor를 선택하는 경로를 피하는 로컬 시작 도우미를 사용했다. EC2 Linux 제품 설정 변경은 아니다.
- 기록·보고서는 architecture에만 위치한다. backend/frontend의 문서 차단·비밀 검사를 적용한다. 기존490개 보관 기록은 수정하지 않는다.
- 문서 무결성94파일, 도우미90조합, 보관490기록 검사 PASS. 기존 긴 문서3개의 분리 권고는 문서 길이 경고이며 런타임 검증을 뜻하지 않는다. backend277/frontend63/architecture609추적 파일의 비밀 패턴 검사 PASS. 코드 저장소의 문서 차단도 PASS.
- 최초 백엔드 원격 CI는 고정 평가 `baseline-system.txt`의 Git 줄바꿈 변환으로 1개 검사 실패(381개 통과)했다. 원래 기준 해시를 바꾸지 않고 해당 파일의 바이트 보존 속성을 추가했다. 스테이징된 기준9파일 해시 일치 및 Linux 관련13개 검사 PASS. 네이티브 Windows 관련 검사 시 임시 폴더 권한 오류가 있어 Linux로 재실행했다.
- 같은 전송 경계 문제를 평가 결과 JSON에도 확인해 architecture에서 원본 바이트 보존을 지정하고 7개 결과 해시 검사를 CI에 추가했다. 원본 응답·기준 해시를 재작성하지 않았다.
- 최종 백엔드 원격 CI는 전체 테스트·DB migration 왕복/정합성·컨테이너 빌드/스모크·저장소 검사를 포함해 PASS. 이번에 만든 tmpfs 테스트 DB와 내부 네트워크만 식별자 확인 후 정리했다. 기존 로컬 DB는 healthy, API 준비 및 프론트 HTTP는 각각200이다.

## 남은 품질 문제와 다음 판단

1. 입력에 필요한 코드가 있는데도 언어 연산·우선순위를 오해하는 경우가 남아 있다. 단순 문맥 확대나 더 큰 모델만으로 해결됐다고 할 수 없다.
2. 검수 호출이 틀린 원인/개선안을 그대로 유지하거나 실제 결함을 제거한다. 독립 단계의 존재 자체는 정확성 증거가 아니다.
3. 실제 PR에서는 아직 보이지 않는 동시 실행 경로를 추측한 질문이 남는다. 질문의 유용성은 형식 검증으로 판정할 수 없다.
4. 다음 품질 실험은 의미 정답의 독립 검수, 개선안의 계약 보존 판정, 실행 가능한 격리 합성 reference oracle를 먼저 구분해야 한다. 제품 저장소 코드를 실행하는 방식으로 확장하지 않는다. 이번 실제 PR의 정답 결함 개수는 알 수 없으므로 미탐률을 계산하지 않는다.

코드 취득·기능 오류 수리는 반영 가능하지만, **공개 배포 전 AI 의미 품질 게이트는 남아 있다**. 이를 테스트/CI 통과나 유료 호출 횟수로 대체하지 않는다.
