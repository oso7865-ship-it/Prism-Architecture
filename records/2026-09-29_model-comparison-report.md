# DeepSeek Flash / Pro 품질 재측정

결론: **현행 조건에서 Pro 일괄 교체는 보류한다.** Pro의 확정 제안 도달은 조금 개선됐지만, 정상 오탐·연산 해석 오류·잘못된 수정 제안이 남았고 지연과 비용이 증가했다. 전체 의미 품질은 미통과다. 제품 모델은 Flash 그대로이며 평가에서만 Pro를 사용했다. 커밋·푸시·배포는 하지 않았다.

[사전 설계](2026-09-29_model-comparison-plan.md) · [집계 원문](quality-evaluations/model-comparison-20260929/summary.json) · [의미 검수](quality-evaluations/model-comparison-20260929/manual-audit.json) · [완료 증거](quality-evaluations/model-comparison-20260929/completion.json)

## 조건과 실제 실행

- 실제 **479회** 호출: Flash239회, Pro240회. 예정480회 중 Flash 초안의 형식 실패1회는 후속 요청을 실행하지 않았다. 자동 재시도0. 같은 CLI 재실행에서 추가 호출0을 확인했다.
- 동일42사례: 기존 합성36개와 공개 PR 최소 재현6개. 조건별2반복. 공통 진단144평가, 제품 흐름168평가, 총312평가다. 새로운 독립 검증셋이나 실제 저장소 PR 전체를 테스트한 것은 아니다.
- 제품 흐름은 현재 초안→근거 검증/빈 답변 재검토 코드다. 공통 진단은 별도 반환값·예외 예측을 추가하므로 제품 점수와 분리한다.
- 두 모델 모두 비추론 모드, temperature0, 출력2,000토큰, 요청60초, 동시 요청 최대4개. 같은 시기에 순서를 섞어 실행했다. 첫 입력156쌍의 시스템·입력 해시가 모두 일치한다. 후속 검증 입력은 각 모델의 초안에 따라 달라진다.
- 실제 `/models`와 각 응답에서 요청 모델 ID를 확인했다. 현재 공식 문서는 `deepseek-flash`를 V4.1-Flash, `deepseek-v4-pro`를 V4-Pro-0813으로 안내한다. Flash가 더 최근 계열이므로 이름만으로 우위를 가정하지 않았다. [공식 모델/가격표](https://api-docs.deepseek.com/quick_start/pricing/), [변경 이력](https://api-docs.deepseek.com/updates/), [실제 모델 조회 기록](quality-evaluations/model-comparison-20260929/model-discovery.json).

## 사용자에게 전달되는 제품 결과

모델당84평가(결함40회·정상44회). 같은 사례의2반복을 포함하므로84개 독립 사례로 해석하지 않는다. 아래의 확정 제안은 `SUPPORTED`와 예상 위치의 일치이며, 원인·수정안까지 모두 맞았다는 뜻은 아니다.

| 측정 | Flash | Pro |
|---|---:|---:|
| 결함이 확정 제안으로 도달 | 35/40 | 36/40 |
| 확정 제안으로 도달하지 못함 | 5/40 | 4/40 |
| 정상 코드에 확정 오탐 | 1/44 | 2/44 |
| 추가 확인 질문 | 4건 | 0건 |
| 최종 처리 미완료 | 1/84 | 1/84 |
| 완료된 리뷰 시간 중앙값 | 3.391초 | 7.297초 |
| 완료된 리뷰 시간 p95 | 4.234초 | 9.312초 |

도달하지 못한5회/4회의 사유는 다르다. Flash는 실제 결함을 설명하면서 질문으로만 처리한2회, 형식 실패1회, CA 환경 변수 결함을 놓친2회다. Pro는 CA 결함2회, range 결함1회, 내용은 올바른 재검토 응답이 파일별 점검 위치 규칙을 어겨 처리되지 못한1회다. 따라서 모두를 단순한 '코드 이해 실패'나 '아무 답도 없음'으로 표현하지 않는다. 미완료 횟수는 도달 실패에 이미 포함되어 있다.

새 합성36사례만의 도달 실패는 Flash3/36·Pro1/36, 공개 최소 재현만은 Flash2/4·Pro3/4였다. 작은 전체 합계 한 건 개선이 어려운 기존 사례의 해결을 뜻하지 않는다.

## 코드 동작 자체를 읽는 진단

모델당72평가, 관측136개다. 표준 예외명의 허용된 별칭을 두 모델에 동일하게 적용했고 원본 strict 점수도 보존했다.

| 측정 | Flash | Pro |
|---|---:|---:|
| 구체 입력의 반환값·예외 정답 | **136/136** | **130/136** |
| 자동 위치 기준 미적중 | 0/36 | 3/36 |
| 정상 오탐 | 0/36 | 1/36 |
| 진단 시간 중앙값 | 1.977초 | 4.117초 |

Pro의 자동 미적중3회 중 중첩 복사1회는 같은 결함을 실제 변경이 전파되는3행에 지적했고 정답 위치는2행만 허용해 생겼다. 이는 실제 미검출로 해석하면 안 된다. 나머지2회는 int 곱셈 오버플로를 놓쳤다. 원래 채점은 보존하고 이 제한을 별도 기록했다.

Pro의 동작 오답6개는 중첩 복사 반환값2개, 뒤집힌 삼항 연산자의 정상 문자열 분기2개, int 곱셈 오버플로2개다. 예를 들어 int끼리 50,000×50,000을 곱한 뒤 long으로 반환하는 코드를 2,500,000,000으로 예측했다. 실제는 int 연산에서 먼저 오버플로되어 -1,794,967,296이 된다. 같은 Pro가 제품 흐름에서는 이 문제를 찾아, 출력 과업에 따른 민감성도 확인했다.

## 자연어 검수에서 확인한 차이

이전 실패와 새 이상 결과를 선별해 원본 코드·계약·초안·최종 결과를 직접 대조했다. 전체312개 응답의 모든 문장에 대한 독립 사람 평가를 완료한 것은 아니다.

| 문제 | 관찰 | 판단 |
|---|---|---|
| 빈 CA 환경 변수 | 두 모델 모두 `None or ''`의 결과와 이후 병합을 잘못 해석해2회씩 최종0건 | 모델 변경만으로 기존 핵심 누락 해결 안 됨 |
| `range(0,n,n)`의 n=0 | Pro 한 회는 올바른 양수 동작 `[0]`을 문제로 지적한 뒤 검증에서 삭제; 실제0입력 결함 미복구 | 맞는 결함을 검증기가 삭제한 사례와 구별 |
| range 수정 제안 | Pro는 n=0 분기와 함께 step1 대안도 제안 | step1은 n=3에서 `[0,1,2]`를 반환해 기존 `[0]` 계약을 깨뜨림 |
| 정상 중첩 복사 | 원본 보존 계약을 충족하는데 조정된 값을 반환해야 한다는 요구를 만들어 냄 | 제품 오탐 Flash1회, Pro2회 |
| null 조건 | Pro는 null 예외를 찾지만 비null 분기의 실제 빈 문자열 대신 의도한 `Ada`를 예측 | 결함 위치 적중과 실행 의미 정확도는 다름 |
| 비교기 설명 | Pro의 검증된 설명에 MAX_VALUE와 MIN_VALUE의 대소 관계가 뒤집힌 문장 | 올바른 `Integer.compare` 제안만으로 전체 설명 통과 불가 |
| Content-Length | Pro 빈 재검토는 2문자/6바이트 원인을 정확히 찾았지만 `file_checks.line=6`이 변경 행2 규칙을 위반 | 모델의 이해 성공과 제품의 결과 수용 실패를 별도 기록 |
| 소유권·경로·UTF-8 | Pro가 올바른 확정 제안을 전달한 반면 Flash 일부는 형식 오류/불필요한 질문 | Pro의 개선점도 존재하나 전면 교체 근거로 부족 |

구체 출력과 원인 분류는 [의미 검수 기록](quality-evaluations/model-comparison-20260929/manual-audit.json)의 키로 개별 results/calls 파일에서 재확인할 수 있다. 경로 사례의 root='/' 범위 모호성은 이전부터 남은 라벨 검수 사항이다. 확인한 형제 경로 반례에는 이 모호성이 영향을 주지 않지만, 모든 경로 입력의 수정안 안전성을 주장하지 않는다.

## 검증·변경 파일·이력

- 추가 backend 평가 코드: `scripts/compare_review_models.py`, `scripts/report_model_comparison.py`, `tests/test_compare_review_models.py`. 제품 코드는 변경하지 않았다. 보고서/원장/응답 기록은 architecture에만 둔다.
- Linux 오프라인 테스트29개 통과(새 비교5개+기존24개), Ruff 검사/형식 검사 통과. 테스트용 비동기 플러그인이 없어 최초2개가 실패한 것은 `asyncio.run` 방식으로 고쳐 같은 검사를 모두 통과했다.
- 최초 모델 조회의 결과 폴더 미생성 오류를 수정한 뒤 실제 조회 성공. 유료 호출 이전 문제였으며 완료 요청 수에는 포함하지 않는다.
- 형식 검증478/479. Flash의 최상위 `citations` 금지 필드1회가 실패했고 Pro는 응답 스키마240/240을 통과했다. 별도로 Pro의 파일별 점검 위치 규칙 실패1회가 있어 스키마 통과와 제품 처리 완료를 구별했다.
- 예약 원장479개·호출 파일479개·결과312개 일치, 미완료 호출0, 동일 키 재호출0, 입력156쌍 일치. 이전 실험1,431회 기록은 그대로 보존했다.
- 이번 승인 캠페인 **1,431+479=1,910/5,000회**, 잔여 **3,090회**. 과거 사용 포함 누적3,473/절대상한6,563회. architecture 원장과 backend 로컬 ignored 사본을 동기화했다.
- `python scripts/validate_docs.py` PASS: 문서104개·로컬 링크457개, 오류0. 기존 긴 문서4개의 크기 안내만 남았다(구조/보안 경고 아님). 양 저장소 `git diff --check`도 통과했고 기존 CRLF 안내는 변경하지 않았다.

## 후속 방향

현재 Flash 유지가 합리적이다. Pro는 확정 제안 분류에서 일부 개선됐지만, 의미 해석·정상 오탐·수정안 계약 보존까지 개선됐다고 볼 수 없다. 이 결론은 **현재 비추론·2,000토큰 조건**에 한정하며 Pro의 추론 모드나 더 큰 출력 예산까지 검증한 결론은 아니다.

다음 실험에서는 모델을 다시 단순 교체하기 전에, 발견한 결함·반환값 예측·수정안의 정상 입력 보존을 서로 대조하고, 잘못된 초안을 기각한 후 실제 코드를 다시 훑는 경로를 분리하는 것이 타당하다. 제품의 변경 행 점검 규칙을 지키면서 올바른 근거를 연결하는 복구도 별도 설계 대상으로 남긴다. 이번 비교 결과를 바탕으로 임의로 운영 검증 규칙을 느슨하게 하거나 제품 모델을 변경하지 않았다.
